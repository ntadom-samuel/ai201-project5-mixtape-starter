# Project 5: Mixtape Bug Hunt — Submission

## Codebase Map

Mixtape is a Flask + SQLAlchemy social music app. It follows a three-layer
architecture: **routes** (HTTP), **services** (business logic), and **models**
(persistence). The bugs all live in the services layer.

### Main files and their roles

| File | Role |
|------|------|
| `app.py` | App factory (`create_app`). Configures SQLite, initializes `db`, registers the four blueprints, calls `db.create_all()`. |
| `models.py` | SQLAlchemy models: `User`, `Tag`, `Song`, `ListeningEvent`, `Rating`, `Playlist`, `Notification`, plus association tables `friendships`, `song_tags`, and `playlist_entries` (which carries `position`, `added_by`, `added_at`). |
| `routes/songs.py` | Endpoints for search, song detail, rating (`POST /songs/<id>/rate`), and recording a listen (`POST /songs/<id>/listen`). |
| `routes/playlists.py` | Create playlist, get playlist metadata, list songs (`GET /playlists/<id>/songs`), add song (`POST /playlists/<id>/songs`). |
| `routes/users.py` | User profile, streak (`GET /users/<id>/streak`), notifications. |
| `routes/feed.py` | "Friends Listening Now" (`GET /feed/<id>/listening-now`) and activity feed. |
| `services/streak_service.py` | Consecutive-day listening streak logic. |
| `services/feed_service.py` | Builds the recent-listeners feed with a 24h recency cutoff. |
| `services/search_service.py` | Song search by title/artist with attached tags. |
| `services/notification_service.py` | Creates notifications on song interactions; also holds `rate_song` and `add_to_playlist`. |
| `services/playlist_service.py` | Playlist creation and ordered song retrieval. |
| `seed_data.py` | Populates the DB with demo users, songs, tags, playlists. |
| `tests/` | Pytest coverage for streaks, search, and playlists (in-memory SQLite). |

### Data flow — "Rate a song" feature

1. Client sends `POST /songs/<song_id>/rate` with JSON `{user_id, score}`.
2. `routes/songs.py::rate()` validates presence of `user_id`/`score`, coerces
   `score` to `int`, and calls `notification_service.rate_song(user_id, song_id, score)`.
3. `rate_song()` validates the 1–5 range, loads the `Song` and rating `User`,
   then either updates the existing `Rating` (enforced unique per user+song) or
   inserts a new one, and commits.
4. The route serializes the `Rating` via `to_dict()` and returns `201`.
5. Separately, `GET /users/<id>/notifications` → `get_notifications()` reads any
   `Notification` rows generated by song interactions.

Trace of the "view playlist" feature for contrast: `GET /playlists/<id>/songs`
→ `playlist_service.get_playlist_songs()` joins `Song` to `playlist_entries`,
filters by playlist, orders by `position`, and returns the serialized list.
